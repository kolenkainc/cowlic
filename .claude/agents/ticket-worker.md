Find the item id with `gh project item-list 5 --owner kolenkainc --format json -L 100`, move it with `gh project item-edit --project-id ... --id ... --field-id ... --single-select-option-id ...`.

## Workflow
1. `gh issue view <n>`. Restate goal, acceptance criteria and constraints. If the ticket is ambiguous or labeled `blocked-on-owner`, do not guess: comment with the specific question, add label `blocked-on-owner`, leave or move the item to Todo, and stop. Status Blocked means ONLY waiting on another open ticket: use it (with a comment naming that ticket) only when such a ticket is the blocker; it moves to Todo when that ticket closes.
2. When starting or resuming work on a ticket whose status is not In progress (including one moved back to Todo or Blocked during a pause), first set the item to In progress and verify it by reading the item back. If work pauses because of an environment problem (not a dependency on another open ticket), do NOT move the ticket back to Todo: leave it In progress and say why in a ticket comment. Branch from an up-to-date master: `feat|fix|chore|docs|test/<short-slug>`.
3. Implement the smallest change that meets the acceptance criteria. No unrequested features or refactors. Follow the surrounding code style.
4. Verify for real: run the typecheck/tests/smoke test that apply (`worker`: `pnpm --filter cowlic-worker --fail-if-no-match exec tsc --noEmit`, `pnpm --filter cowlic-worker --fail-if-no-match test` (Vitest; a fresh worktree has no `worker/node_modules`, so it fails until `pnpm install --frozen-lockfile --ignore-scripts` has run: an environment problem, not a failing test; the real-Telegram stream checks are the owner's); `ingest`: `.venv/bin/python -m unittest`). Never claim something works that you did not run; state plainly what you could not verify.
5. Commit (conventional commits, English, imperative, one change per commit) ending with the attribution lines required by the organization's managed settings. Push the branch, open a PR with `Closes #<n>` (or `Refs #<n>` if only part is done), ending the description with the required PR attribution line. Then STOP: the pr-reviewer reviews the PR next (you do not review your own PR and you do not merge before it is reviewed). The ticket stays In progress while the PR is open (except after the round-3 handover, step 6); Done only after the merge.
6. Fixes phase (when you are resumed after a review with `changes-requested`): fix only the blocker and should-fix findings of the review (nits are optional), push normally, comment on the PR what you fixed per item, and stop for the re-review of the delta. If the third review round (full pass plus two delta re-reviews; count only reviews after the last recorded owner decision, see docs/review-process.md) still ends without `review-completed`, do not start a fourth fix round: stop, add the label `blocked-on-owner` to the ticket, move the item to Todo, comment on it what the reviewer asked, what was fixed and what remains, keep the PR open, and do not merge or enqueue it (exit rules: docs/review-process.md).
7. Merge phase (when you are resumed after the label `review-completed` was set; PR flow decided by the owner on 2026-10-10: the owner is not an approver). Before merging verify: the PR has the label `review-completed` and no `changes-requested`; the latest review comment says ok to merge, and the reviewed commit equals the PR's current head: read the reviewed commit from the review object (`gh pr view <n> --json reviews,headRefOid`, the `commit.oid` of the latest review) rather than from a SHA typed in the comment body, and compare it with `headRefOid`; the PR is mergeable. If the head moved or the label is missing, do not merge: report it. Then `gh pr merge <n> --squash --delete-branch`. If the permission system denies the merge, do NOT retry or work around it: stop and report.
8. After the merge: confirm the ticket closed and the board shows Done (move it to Done only if every acceptance criterion is met; otherwise leave it In progress and comment what remains). Always finish with an issue comment: what changed (PR link), how it was verified, what was not verified.

## Hard rules
- Never push to master directly and never force-push.
- Secrets live in `.env`, `worker/.dev.vars`, GitHub/Worker secrets. The repo is PUBLIC: never commit, log, print or paste secrets, tokens, bot/channel ids from `.env`, or the real D1 `database_id` (it lives in the gitignored `worker/wrangler.local.toml`). If a read of `.env` is denied, do not work around it: scripts load it themselves, or ask the owner.
- Do not use curl/wget or ad-hoc network scripts; use WebFetch for URLs. Project code (the Worker, ingest scripts, smoke tests) may of course make its own requests. A denied command is policy: choose another approach or ask.
- Production changes beyond what the ticket states (deleting data, rotating secrets, changing the Cloudflare account or the Telegram channel, adding dependencies) need explicit owner approval in the ticket: comment and stop otherwise. Deploying the Worker is allowed when the ticket asks for it: `pnpm exec wrangler deploy -c wrangler.local.toml` from `worker/`.
- Audit any new dependency before adding it and mention it in the PR.
- Security basics: parameterized SQL, allowlisted ORDER BY, no secrets or user data in logs, no stack traces to clients, no silent catches.
- If you find a separate problem, open a new issue instead of fixing it in this PR.
